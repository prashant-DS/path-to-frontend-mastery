# System Design + Frontend Implementation — Round 2

## Overview

This round was a combination of product ideation, API-driven system design, and frontend implementation.

The interviewer provided a set of REST-like APIs:

- `GET /articles`
- `GET /articles/:id`
- `GET /comments`
- `GET /comments/:id`
- `GET /users`
- `GET /users/:id`

The task was to ideate a product using as many of these APIs as possible and then implement the product from scratch.

---

## Product Ideation

We spent roughly 30 minutes discussing what kind of product could be built around the provided APIs.

I decided to go in the direction of a Medium-like blogging platform.

The initial idea was to have two main sections/tabs:

### Articles / Posts

Use the articles APIs to:

- Fetch and display the list of articles.
- Show basic article information in the listing.
- Open an individual article using `GET /articles/:id`.
- Show the article details.
- Fetch and display comments for an article.

### Authors

Use the users APIs to:

- Fetch and display authors.
- Allow users to browse articles/authors from the author side.
- Fetch individual user details using `GET /users/:id`.

### Comments

Use the comments APIs to:

- Fetch comments associated with an article.
- Display comments inside the article details page.
- Use individual comment details where required.

The goal was to use as many of the provided APIs as possible rather than building a feature around only one or two endpoints.

---

## Interview Format

The product ideation started directly from the APIs provided by the interviewer.

The flow was effectively:

1. Given a predefined set of APIs.
2. Come up with a product that could use those APIs.
3. Define the major user flows and features.
4. Try to incorporate as many of the APIs as possible.
5. Implement the product from scratch.

A more conventional product-development flow would generally be:

1. Identify a user problem / pain point.
2. Define the product or feature that solves the problem.
3. Define the requirements and user flows.
4. Design the APIs/data model needed to support those requirements.
5. Build the frontend using those APIs.

This distinction was discussed during the interview because the task started from the API contract rather than from a predefined product requirement.

---

## Implementation

After the product ideation phase, I started implementing the application from scratch in CodeSandbox.

I also explicitly confirmed whether styling was expected as part of the implementation. The interviewer confirmed that it was, so the task included both:

- Functional implementation
- UI/styling

There wasn't a clearly defined priority or minimum feature set after the ideation phase, so the implementation scope remained fairly broad.

---

## Time Constraint

The ideation phase took roughly 30 minutes.

Because we had discussed a relatively large product scope, implementing even half of the planned functionality in the remaining time became difficult.

I started implementing the core flows, but the available time became a major constraint.

---

## Interview Experience

One of the challenges during this round was that there was limited interaction or feedback from the interviewer during the implementation phase.

After the initial ideation, the implementation phase became fairly one-sided.

Since there wasn't much guidance on which parts of the proposed product should be prioritized, I continued implementing based on the scope we had discussed earlier.

As the remaining time decreased, it became difficult to complete a meaningful portion of the originally proposed product.

---

## Reflection

This round did not go as well as expected, and I was not selected after this round.

The main learning from this round was the importance of scoping the implementation after product ideation.

For a time-constrained frontend interview, after defining a broad product, it would be useful to explicitly establish:

- The minimum viable feature set
- The primary user flow
- Which APIs are mandatory to demonstrate
- Which features can be treated as follow-ups
- How much time should be allocated to functionality vs styling

The interview combined multiple areas:

- Product ideation
- Requirements definition
- API utilization
- Frontend architecture
- UI implementation
- Styling

Because of the breadth of the exercise, establishing a clear MVP before implementation would have been important for managing the remaining time.
