# HackerRank React Assessment — Round 2

## Setup

- React project was already scaffolded.
- The application had a large asset list (~100k assets).
- Each asset contained fields like:
  - `id`
  - `title`
  - `type`
  - `brand`
  - `sizeBytes`
  - `updatedAt`
  - `thumbnailUrl`
  - `isFavorite`
- UI had:
  - Text input for searching by title
  - Select input for filtering by asset type
  - Large list/grid of matching assets
  - Favorite/unfavorite action

The first part of the round was a senior-level code review. I was asked to review the existing implementation, identify performance/React issues, and discuss how I would optimize them.

After the review, we narrowed it down to three optimizations to actually implement:

1. Fix the React `key`
2. Optimize the `visible` list computation
3. Prevent unnecessary `AssetCard` re-renders with `React.memo`

## Initial Code Given

```jsx
import React, { useState, useMemo, useCallback } from "react";
import "./App.css";

// Assume this is an API response
const generateAssets = (count) => {
  const types = ["Image", "Video", "Article"];

  return Array.from({ length: count }, (_, i) => ({
    id: `asset-${i}`,
    title: `ABC News Asset ${i}`,
    brand: "ABC News",
    type: types[i % types.length],
    sizeBytes: Math.floor(Math.random() * 5_000_000_000),
    updatedAt: Date.now() - Math.floor(Math.random() * 1e10),
    thumbnailUrl: `https://picsum.photos/seed/${i}/80/60`,
    isFavorite: false,
  }));
};

const formatBytes = (bytes) => {
  if (!bytes) return "0 B";

  const units = ["B", "KB", "MB", "GB"];
  let n = bytes;
  let i = 0;

  while (n >= 1024 && i < units.length - 1) {
    n /= 1024;
    i++;
  }

  return `${n.toFixed(1)} ${units[i]}`;
};

export const AssetCard = ({ asset, onToggleFavorite, style }) => {
  const formattedSize = formatBytes(asset.sizeBytes);
  const formattedDate = new Date(asset.updatedAt).toLocaleString();

  return (
    <div className="asset-card" style={style}>
      <img
        src={asset.thumbnailUrl}
        alt={asset.title}
        loading="lazy"
      />

      <div className="asset-card__meta">
        <h3>{asset.title}</h3>
        <p>{asset.brand} · {asset.type}</p>
        <p>{formattedSize} · {formattedDate}</p>

        <button onClick={() => onToggleFavorite(asset.id)}>
          {asset.isFavorite ? "★ Favorited" : "☆ Favorite"}
        </button>
      </div>
    </div>
  );
};

const ALL_ASSETS = generateAssets(100000);
const TYPES = ["All", "Image", "Video", "Article"];

const App = () => {
  const [query, setQuery] = useState("");
  const [type, setType] = useState("All");
  const [assets, setAssets] = useState(ALL_ASSETS);

  const visible = assets
    .filter((a) => type === "All" || a.type === type)
    .filter((a) =>
      a.title.toLowerCase().includes(query.toLowerCase())
    )
    .sort((a, b) => a.title.localeCompare(b.title));

  const toggleFavorite = (id) => {
    setAssets((prev) =>
      prev.map((a) =>
        a.id === id
          ? { ...a, isFavorite: !a.isFavorite }
          : a
      )
    );
  };

  return (
    <div>
      <input
        placeholder="Search ABC News assets…"
        value={query}
        onChange={(e) => setQuery(e.target.value)}
      />

      <select
        value={type}
        onChange={(e) => setType(e.target.value)}
      >
        {TYPES.map((t) => (
          <option key={t} value={t}>
            {t}
          </option>
        ))}
      </select>

      <div className="asset-grid">
        {visible.map((asset, i) => (
          <AssetCard
            key={i}
            asset={asset}
            onToggleFavorite={(id) => toggleFavorite(id)}
            style={{ marginBottom: 8 }}
          />
        ))}
      </div>
    </div>
  );
};

export default App;
```

## Code Review

### 1. React `key`

The first issue I noticed was:

```jsx
{visible.map((asset, i) => (
  <AssetCard key={i} />
))}
```

The array index was being used as the React key.

This can cause incorrect component identity when the list is filtered or reordered because the same index can represent a different asset after the list changes.

The correct approach is to use the stable asset ID:

```jsx
<AssetCard key={asset.id} />
```

---

### 2. Large List / Virtualization

The list could contain around 100k assets, and rendering all of them was causing the UI to become very laggy and freeze during interactions.

I suggested list virtualization using a library such as `react-window` instead of implementing virtualization from scratch.

The idea was to render only the elements currently visible in the viewport rather than putting the entire 100k-item list into the DOM.

---

### 3. `visible` Calculation

The original implementation calculated the entire visible list in one chain:

```js
const visible = assets
  .filter((a) => type === "All" || a.type === type)
  .filter((a) =>
    a.title.toLowerCase().includes(query.toLowerCase())
  )
  .sort((a, b) => a.title.localeCompare(b.title));
```

We discussed memoizing this calculation.

A straightforward approach would be:

```js
const visible = useMemo(() => {
  return assets
    .filter((a) => type === "All" || a.type === type)
    .filter((a) =>
      a.title.toLowerCase().includes(query.toLowerCase())
    )
    .sort((a, b) => a.title.localeCompare(b.title));
}, [assets, type, query]);
```

However, I pointed out that this still means the entire computation is invalidated whenever any of `assets`, `type`, or `query` changes.

Since these account for most of the state mutations, simply memoizing the entire chain would not provide as much benefit.

### Approach I Suggested

Split the computation into separate stages and memoize them independently:

```js
const typeFilteredAssets = useMemo(() => {
  return assets.filter(
    (asset) => type === "All" || asset.type === type
  );
}, [assets, type]);

const queryFilteredAssets = useMemo(() => {
  return typeFilteredAssets.filter((asset) =>
    asset.title.toLowerCase().includes(query.toLowerCase())
  );
}, [typeFilteredAssets, query]);
```

The idea is that if only `query` changes:

- `assets` has not changed.
- `type` has not changed.
- `typeFilteredAssets` remains the same.
- Only the query filtering needs to run again.

So instead of recalculating both filters over the full 100k assets, we reuse the result of the first filtering stage.

---

### 4. Sorting

We also discussed the `.sort()` being performed every time the filtering chain runs.

Since the sort order was independent of both the type filter and search query, there was no reason to repeatedly sort the list.

The approach I suggested was to sort the data when initially populating the `assets` state itself.

Instead of:

```js
const [assets, setAssets] = useState(ALL_ASSETS);
```

use the sorted data:

```js
const sortedAssets = [...ALL_ASSETS].sort(
  (a, b) => a.title.localeCompare(b.title)
);

const [assets, setAssets] = useState(sortedAssets);
```

This way, the filtering operations work on an already-sorted dataset.

## Optimizations We Actually Implemented

After the review, we narrowed the implementation down to three specific changes.

### 1. Fix the React `key`

Changed:

```jsx
key={i}
```

to:

```jsx
key={asset.id}
```

---

### 2. Memoize the Visible Data

We introduced memoization for the expensive filtering computation.

The important discussion was that instead of blindly memoizing the entire calculation with:

```js
[assets, type, query]
```

it is better to split the filtering stages so that a change in one filter does not unnecessarily repeat the previous filtering stage.

For example:

```js
const typeFilteredAssets = useMemo(() => {
  return assets.filter(
    (asset) => type === "All" || asset.type === type
  );
}, [assets, type]);

const visible = useMemo(() => {
  return typeFilteredAssets.filter((asset) =>
    asset.title.toLowerCase().includes(query.toLowerCase())
  );
}, [typeFilteredAssets, query]);
```

---

### 3. Memoize `AssetCard`

The `AssetCard` component was re-rendering whenever the parent rendered.

We changed it to:

```js
export const AssetCard = React.memo(
  ({ asset, onToggleFavorite, style }) => {
    // ...
  }
);
```

We also discussed that `React.memo` only provides the expected benefit when the props have stable references.

The original code had:

```jsx
onToggleFavorite={(id) => toggleFavorite(id)}
```

which creates a new function reference on every render.

So `toggleFavorite` should be stabilized with `useCallback`:

```js
const toggleFavorite = useCallback((id) => {
  setAssets((prev) =>
    prev.map((a) =>
      a.id === id
        ? { ...a, isFavorite: !a.isFavorite }
        : a
    )
  );
}, []);
```

and then passed directly:

```jsx
onToggleFavorite={toggleFavorite}
```

We also discussed the inline style:

```jsx
style={{ marginBottom: 8 }}
```

because it creates a new object reference on every render. For `React.memo` to work effectively, object props also need stable references.

---

## Other Optimizations Discussed

These were discussed during the review but were not part of the three optimizations we implemented.

### Web Worker

Since filtering a very large dataset can be CPU-intensive and block the main thread, we discussed moving expensive filtering work to a Web Worker.

### Search Input

Since every query change can trigger filtering over a 100k-item dataset, we discussed:

- Debouncing the search input
- `useDeferredValue` as a React-based approach to keep the input responsive while the list update happens at a lower priority
