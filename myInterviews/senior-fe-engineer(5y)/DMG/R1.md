# Discussion + DSA on Paper — Round 1

## Overview

On-site, face-to-face round. No laptop, no editor, no compiler — everything was written
on paper, dry run manually, and then discussed out loud.

The round had two halves:

1. An open, discussion-style section: intro, followed by questions about how I use AI
   models and AI agents in day-to-day engineering work.
2. Two DSA/JS questions, both written and dry run on paper.

---

## AI Discussion

### 1. How do you choose an AI model? On what parameters?

Was asked how I pick between models, and what parameters drive that choice.

My answer was that it depends on the shape of the task:

- **Heavy reasoning or writing-type work** — Opus. Long-form writing, deep reasoning,
  anything where the quality of the thinking matters more than the turnaround.
- **General coding and general discussion** — Sonnet. Day-to-day implementation, code
  questions, back-and-forth discussion where speed and cost matter.
- **Plain rewriting / light text work** — Haiku. Rephrasing, cleaning up wording, and
  similar mechanical text edits where no real reasoning is involved.

### 2. How do you approach a big feature with AI?

Explained the workflow I actually use, which is staged and deliberately does not jump
straight to code:

1. **Brainstorm first.** I start with a brainstorming step whose only job is to discuss
   possible approaches and the pros and cons of each. No planning, no implementation,
   no file edits — purely converging on an approach.
2. **Plan.** Once the approach is finalised, build a plan from it.
3. **Implement.** Only then start implementation, driven by that plan.

Also mentioned keeping parallelism in mind during implementation — using subagents for
independent chunks of work wherever the plan allows it.

## DSA Questions

Both questions were on paper. Nothing was run; the expectation was to write the code,
dry run it by hand, and defend it in discussion.

### 1. Flatten a Nested Object

Given an object that may contain nested objects, arrays, or primitives, produce a
flattened object with no nesting, where the keys encode the original path.

The key format used dots for object keys and bracket notation for array indices, e.g.
`address[0].city`.

I don't remember the exact object I was given — it was on paper and nothing was saved.
This is an example of the same shape, covering primitives, nested objects, arrays of
objects, and arrays of primitives:

```js
const input = {
  id: 1,
  name: "John",
  isActive: true,
  profile: {
    age: 30,
    social: {
      twitter: "@john",
    },
  },
  address: [
    {
      city: "Delhi",
      pin: 110001,
      landmarks: ["Metro", "Mall"],
    },
    {
      city: "Pune",
      pin: 411001,
      landmarks: [],
    },
  ],
  tags: ["admin", "beta"],
};
```

Expected output:

```text
{
  "id": 1,
  "name": "John",
  "isActive": true,
  "profile.age": 30,
  "profile.social.twitter": "@john",
  "address[0].city": "Delhi",
  "address[0].pin": 110001,
  "address[0].landmarks[0]": "Metro",
  "address[0].landmarks[1]": "Mall",
  "address[1].city": "Pune",
  "address[1].pin": 411001,
  "tags[0]": "admin",
  "tags[1]": "beta"
}
```

Worth noting: `address[1].landmarks` is an empty array, so it contributes no key at all
to the output. Edge cases like that (empty arrays, empty objects) were part of the
discussion.

The approach was a recursive walk: for every key, if the value is a nested object or
array, recurse with the accumulated key prefix (dot for object keys, `[i]` for array
indices); if it is a primitive, write it into the result under the prefixed key.

After writing it, I dry ran it by hand and walked through the recursion depth by depth.

### 2. Move All Zeros to the Front

Given an array of `0`s and `1`s, rearrange it so all the zeros come first and all the
ones come at the end.

Example:

```text
input  → [0, 1, 0, 1, 1, 0]
output → [0, 0, 0, 1, 1, 1]
```

#### How the discussion went

I started with a naive option using `map`/rebuilding the array, then we moved toward
optimising it.

**First optimisation — pointers from both ends.** Keep a `left` pointer at the start, a
`right` pointer at the end, and iterate: push zeros toward the left, ones toward the
right.

The interviewer pushed back on this: that is effectively three pointers (`left`,
`right`, and the iterator). Could it be done with two?

**Second attempt.** I dropped the `right` pointer and kept only `left` and the iterating
pointer. The invariant: everything to the left of `left` is a zero. Iterate to the end
swapping zeros into the `left` position and advancing `left`. By the end, all zeros are
on one side and, as a consequence, all ones are on the other.

My read was that he still was not satisfied — he seemed to be looking for the exact
textbook two-pointer formulation rather than this reasoning-from-the-invariant version.
